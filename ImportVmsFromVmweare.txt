مهاجرت از VMware به Proxmox VE، امروزه با وجود ابزارهای داخلی بسیار ساده‌تر از گذشته شده است. Proxmox از نسخه **8.2** یک **ESXi Import Wizard** داخلی معرفی کرده که در نسخه‌های **9.x** به روش استاندارد و توصیه‌شده تبدیل شده است. با این حال، موفقیت یک مهاجرت حرفه‌ای به برنامه‌ریزی دقیق پیش و اعتبارسنجی کامل پس از آن بستگی دارد.

---

### 🗺️ ۱. دو مسیر اصلی مهاجرت

**مسیر اول: ESXi Import Wizard (توصیه‌شده برای اکثر تیم‌ها)**
این روش برای محیط‌هایی است که به ESXi از طریق شبکه دسترسی دارند و ماشین‌های مجازی می‌توانند به صورت آنلاین یا آفلاین وارد شوند.

1.  **افزودن ESXi به عنوان منبع Import**: در رابط وب Proxmox، به مسیر **Datacenter → Storage → Add → ESXi** بروید و آدرس IP یا دامنه ESXi را همراه با اعتبارنامه‌های مدیریتی وارد کنید. اگر ESXi از گواهی خودامضا استفاده می‌کند، گزینه **Skip Certificate Verification** را فعال کنید.
2.  **انتخاب و Import**: جادوگر به ESXi متصل شده و لیست ماشین‌های مجازی را نمایش می‌دهد. پس از انتخاب VM، تنظیمات نگاشت‌شده را بررسی کرده و Import را آغاز کنید. Proxmox به صورت خودکار دیسک‌ها را از طریق یک فایل‌سیستم FUSE که بین PVE و ESXi قرار می‌گیرد، واکشی می‌کند.
3.  **محدودیت‌های Import Wizard**: این روش از **ESXi 6.5 تا 8.0** تست شده است. **دیسک‌های مبتنی بر vSAN پشتیبانی نمی‌شوند** (راه‌حل: ابتدا دیسک‌ها را به یک Datastore معمولی منتقل کنید). همچنین **اسنپ‌شات‌ها از طریق Import Wizard منتقل نمی‌شوند** و باید قبل از مهاجرت حذف یا Consolidate شوند.

**مسیر دوم: روش دستی (Export + qemu-img)**
این روش **Fallback جهانی** است و برای نسخه‌های قدیمی ESXi، محیط‌های vSAN یا زمانی که کنترل کامل روی هر مرحله می‌خواهید، مناسب است.

1.  **Export از vSphere**: ماشین مجازی را خاموش کرده و از vSphere Client آن را به صورت **OVA/OVF** اکسپورت کنید. یا مستقیماً فایل‌های **VMDK** را از Datastore کپی کنید.
2.  **انتقال فایل‌ها**: فایل‌های اکسپورت‌شده را با `scp`، `rsync` یا یک اشتراک NFS به هاست Proxmox منتقل کنید.
3.  **تبدیل دیسک با `qemu-img`**: فرمت VMDK توسط استوریج‌های Proxmox پشتیبانی نمی‌شود و باید تبدیل شود:
    ```bash
    # برای استوریج‌های فایل‌محور (Directory/NFS) -> QCOW2
    qemu-img convert -p -f vmdk -O qcow2 source.vmdk target.qcow2

    # برای استوریج‌های بلوک‌محور (ZFS/LVM/Ceph) -> RAW
    qemu-img convert -p -f vmdk -O raw source.vmdk target.raw
    ```
    
4.  **ایجاد VM و Import دیسک**: یک VM جدید در Proxmox با مشخصات مشابه (CPU، RAM) ایجاد کنید، سپس دیسک تبدیل‌شده را با `qm importdisk` وارد کرده و به VM متصل کنید.

### 📋 ۲. آماده‌سازی حیاتی پیش از مهاجرت

**الف) درایورهای VirtIO (فقط برای ویندوز)**
این **مهم‌ترین و حیاتی‌ترین گام** برای ماشین‌های ویندوزی است. VirtIO درایورهای نیمه‌مجازی‌سازی‌شده‌ای هستند که عملکرد بسیار بهتری ارائه می‌دهند، اما اگر سیستم‌عامل مهمان آن‌ها را نداشته باشد، با **صفحه آبی (BSOD) و خطای `INACCESSIBLE_BOOT_DEVICE (0x0000007B)`** مواجه می‌شود.

*   **راه‌حل**: **قبل از مهاجرت**، ISO درایورهای VirtIO را دانلود کرده و درایورهای **VirtIO SCSI** (برای دیسک) و **VirtIO NetKVM** (برای شبکه) را درون ویندوز نصب کنید. همچنین می‌توانید از یک اسکریپت PowerShell برای Preload کردن درایور `viostor` استفاده کنید تا ویندوز بدون نیاز به ری‌استارت، برای مهاجرت آماده شود.
*   **برای لینوکس**: ماژول‌های VirtIO از کرنل 2.6.24 به بعد به صورت داخلی وجود دارند و نیازی به نصب جداگانه نیست.

**ب) هماهنگ‌سازی حالت بوت (BIOS/UEFI)**
حالت بوت مبدأ (Legacy BIOS یا UEFI) را دقیقاً در تنظیمات VM در Proxmox بازتولید کنید. ناهماهنگی در این مورد یکی از شایع‌ترین دلایل بوت نشدن ماشین است. اگر VM مبدأ از **vTPM** استفاده می‌کند، باید قبل از مهاجرت آن را غیرفعال کنید، زیرا ممکن است در حین Import مشکل ایجاد کند.

**ج) حذف اسنپ‌شات‌ها و آماده‌سازی سیستم‌عامل مهمان**
*   **حذف/Consolidate کردن اسنپ‌شات‌ها**: اسنپ‌شات‌ها پیچیدگی دیسک را افزایش داده و سرعت مهاجرت را کاهش می‌دهند (و از طریق Import Wizard منتقل نمی‌شوند).
*   **غیرفعال کردن رمزنگاری دیسک**: در صورت فعال بودن، باید غیرفعال شود.
*   **تنظیم شبکه روی DHCP (موقت)**: برای جلوگیری از تعارض IP پس از تغییر نام کارت شبکه، بهتر است موقتاً تنظیمات IP را روی DHCP قرار دهید و پس از مهاجرت، IP استاتیک را بازگردانید.

---

### 💾 ۳. ذخیره‌سازی: طراحی و تغییرات لازم

**الف) طراحی استوریج مقصد**
Proxmox از طیف گسترده‌ای از استوریج‌ها پشتیبانی می‌کند: **LVM-Thin** (رایج‌ترین پیش‌فرض)، **ZFS** (برای Snapshot و Self-Healing)، **Ceph** (برای کلاستر و High Availability) و **NFS/iSCSI** (برای ذخیره‌سازی اشتراکی). استوریج مقصد باید از نظر **الگوی نوشتن (Write Pattern)** با بار کاری شما سازگار باشد.

**ب) استراتژی انتقال دیسک**
*   **برای حجم کم**: روش Export/Import یا Import Wizard کافی است.
*   **برای حجم بالا (چند صد گیگابایت یا ترابایت)**: استفاده از یک **LUN موقت مشترک** بین vSphere و Proxmox توصیه می‌شود. ابتدا دیسک‌ها را با Storage vMotion به این LUN منتقل کنید، سپس VM را در Proxmox ایجاد کرده و دیسک‌ها را از همان LUN به VM متصل کنید. پس از تأیید صحت، دیسک‌ها را به استوریج نهایی مهاجرت دهید.

**ج) انتخاب فرمت دیسک**
*   **QCOW2**: برای استوریج‌های فایل‌محور (Directory/NFS) مناسب است و از **Snapshot** پشتیبانی می‌کند.
*   **RAW**: برای استوریج‌های بلوک‌محور (ZFS/LVM/Ceph) عملکرد بهتری دارد.

### 🌐 ۴. شبکه: نگاشت و تغییرات پس از مهاجرت

**الف) بازسازی توپولوژی شبکه**
vSwitchها، Port Groupها و VLANهای VMware باید در Proxmox با **Linux Bridge** و **VLAN-aware Bridge** بازسازی شوند. استفاده از VLAN-aware Bridge انعطاف‌پذیری بالایی برای نگاشت Port Groupهای ESXi فراهم می‌کند.

**ب) تغییر نام کارت شبکه**
پس از مهاجرت، نام کارت شبکه در سیستم‌عامل مهمان معمولاً تغییر می‌کند (مثلاً از `ens160` به `ens18`). اگر IP استاتیک تنظیم شده باشد، باید فایل پیکربندی شبکه در مهمان به‌روزرسانی شود.

**ج) تغییر مدل NIC به VirtIO**
برای ویندوز، پس از نصب درایور VirtIO NetKVM، مدل NIC را در تنظیمات VM از **`e1000`** (شبیه‌سازی Intel) به **`VirtIO`** تغییر دهید تا عملکرد شبکه بهینه شود.

### ✅ ۵. اعتبارسنجی پس از مهاجرت

پس از بوت، این موارد را به ترتیب بررسی کنید:
1.  **بوت شدن سیستم‌عامل** و عدم وجود خطای درایور.
2.  **شبکه**: IP، Gateway، DNS و اتصال به VLAN صحیح.
3.  **سرویس‌ها**: دسترسی به SSH/RDP/HTTP و اتصال به سرویس‌های وابسته (AD، DNS، دیتابیس).
4.  **عملکرد (Performance)**: بررسی I/O دیسک، مصرف CPU و حافظه. در صورت نیاز، کنترلر دیسک را از **IDE/SATA** به **VirtIO SCSI single** تغییر داده و گزینه **IO Thread** را فعال کنید.
5.  **نصب QEMU Guest Agent**: `qemu-guest-agent` را نصب کرده و در تنظیمات VM فعال کنید تا امکان Graceful Shutdown و نمایش صحیح IP فراهم شود.

### 💡 ۶. Best Practiceهای عملیاتی برای DevOps و زیرساخت

**الف) خودکارسازی و امنیت با API Token**
برای ابزارهای IaC (Terraform، Ansible) **هرگز از رمز عبور root استفاده نکنید**. یک **API Token** با حداقل دسترسی لازم ایجاد کرده و پس از پایان مهاجرت آن را **ابطال** کنید.

**ب) جداسازی شبکه مهاجرت**
ترافیک Import و Live Migration را از شبکه مدیریت (Corosync) و شبکه ذخیره‌سازی جدا کنید. یک VLAN اختصاصی برای Migration در نظر بگیرید و آن را در **Datacenter → Options → Migration Settings** تنظیم کنید.

**ج) Serialize کردن Importها**
اگرچه Import Wizard می‌تواند چندین Import را همزمان انجام دهد، اما به دلیل **محدودیت اتصال API در ESXi** (که پس از رسیدن به سقف، کلاینت‌ها را حدود ۳۰ ثانیه بلاک می‌کند) و خطر Overload شدن ESXi، توصیه می‌شود Importها را **به صورت سری (Serialize)** انجام دهید.

**د) استراتژی Pilot و Rollback**
قبل از مهاجرت انبوه، یک **پنجره آزمایشی** با چند VM غیرحیاتی اجرا کنید و فرآیند **Rollback** را تمرین نمایید. ماشین‌های High-Risk (Domain Controller، دیتابیس اصلی) را در موج آخر و پس از تأیید کامل Pilot مهاجرت دهید. از ماشین‌های مبدأ **پشتیبان کامل** تهیه کرده و صحت بازیابی آن‌ها را **قبل از** مهاجرت تست کنید.

**ه) پرهیز از Live Restore در محیط Production**
گزینه **Live Restore** در Import Wizard اگرچه زمان قطعی را کاهش می‌دهد، اما در صورت شکست Import، **تمام داده‌های نوشته‌شده از زمان شروع Import از بین می‌رود**. Proxmox خود صراحتاً توصیه می‌کند که این مکانیزم ابتدا روی یک VM آزمایشی تست شود و در شبکه‌های با پهنای باند کم یا نرخ خطای بالا استفاده نشود. برای محیط Production، **خاموش کردن VM در سمت ESXi** و سپس Import، ایمن‌ترین رویکرد است.
